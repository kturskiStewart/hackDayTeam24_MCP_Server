tenant. Everything under [examples/](examples/) is generated by

## 1. Executive access review

**Problem.** A leader asks "what access does Adam have?" Answering means opening
the SailPoint UI, finding the right Adam, and clicking through roles, access
profiles and entitlements across several systems. The result is rarely written
down in a form an auditor can keep.

**Solution.** Ask in plain language. The assistant resolves who you mean, gathers
the full access picture in about three seconds, writes the raw evidence to a CSV,
and summarizes it for a non-technical reader.

**Example prompts**

- "What access does Adam Kennedy have?"
- "Give me a summary of Janet Washington's access, and anything privileged."

**Flow**

1. `search_identities` finds candidates. If more than one person matches, the
   assistant lists every candidate with job title, department and manager, and
   asks which one. It never guesses.
2. Once the user picks, `analyze_identity_access(identity_id)`:
   - pulls roles, access profiles, entitlements and accounts in one Search API call,
   - expands each access profile / role in parallel to learn which bundle grants
     which entitlement (direct vs. inherited),
   - looks up entitlement owner and privilege level in batches,
   - writes every row to a CSV (Excel-friendly) and returns a compact digest.
3. The assistant turns the digest into a leadership summary and gives the CSV path.

**Evidence**

| File | What it shows |
| --- | --- |
| [identity_adam_kennedy.json](examples/identity_adam_kennedy.json) | Step 1: the search result the user picks from |
| [analyze_identity_access_adam_kennedy.json](examples/analyze_identity_access_adam_kennedy.json) | Step 2: the digest the assistant summarizes |
| [access_adam_kennedy.csv](examples/access_adam_kennedy.csv) | The exported raw data (18 rows) |
| [access_janet_washington.csv](examples/access_janet_washington.csv) | A manager with more access (26 rows) |

Adam Kennedy (Payroll Analyst II, Accounting): 10 entitlements, 4 access profiles
and 4 accounts across PRISM and Active Directory; 7 of the entitlements come
through access profiles and 3 were assigned directly. Each CSV row records the
type, source, description, whether it is privileged, who owns it, and which
bundle granted it.

**Known limits**

- The summary is written by the assistant from the digest; the server has no
  model of its own. Quality depends on the client model.
- The demo tenant has no roles assigned to anyone, so role expansion has never
  run against real data (it is wrapped so a failure only adds a note).
- Owner and privileged columns are empty/false throughout the demo data, so
  privileged-access flagging is untested on real positives.
- At most 40 roles/access profiles are expanded per identity, to bound the number
  of API calls.

## 2. Access request tracking

**Problem.** In many organizations only a manager can request access for their
team. The employee who needs the access never sees the ticket, and the manager
has no easy view of what is still waiting on them. Both end up asking IT.

**Solution.** Two views of the same workflow, in plain language.

*Requester / beneficiary* -- `get_access_request_status`

- "Is there any pending access request for me?"
- "What's the status of the access my manager asked for?"
- "What was recently approved?"
- "What requests did I submit for my team?"

Requests are bucketed into plain statuses (`pending_approval`, `in_progress`,
`completed`, `rejected`, `failed`, `cancelled`), and pending ones say who they are
`waiting_on`. A request not yet at a human approver reports its automated
`current_phase` (for example `SOD_PHASE`) so "in progress" is never a dead end.

*Approver* -- `get_approvals`

- "Do I still need to approve anything?"
- "What did I approve in the last two weeks?"

Pending approvals come back oldest first, so the most overdue is on top.
`include_completed=true` adds recent decisions with who decided and why.

*The deliverable* -- `export_access_request_report`

"Give me a report of Adam's access requests." Writes a sheet (CSV for Excel, plus a
printable HTML page) with pending items first, then in-progress, recently approved
and not-granted. Each row names the access, who needs to approve it or who
approved it, and carries a one-or-two-sentence note: what the access is (the
item's own description, quoted) plus where it stands. The note is built from the
request data rather than written by a model, so the sheet is identical every run
and can be kept as evidence.

For pending requests the approver comes from the approvals API, because the
request record has no name for "all owners" approval schemes.

**Evidence**

| File | What it shows |
| --- | --- |
| [access_requests_adam_kennedy.html](examples/access_requests_adam_kennedy.html) | The end-user sheet (open in a browser, or print) |
| [access_requests_adam_kennedy.csv](examples/access_requests_adam_kennedy.csv) | The same sheet for Excel |
| [access_request_report_adam_kennedy.json](examples/access_request_report_adam_kennedy.json) | What the tool returns to the assistant |
| [access_request_status_adam_kennedy.json](examples/access_request_status_adam_kennedy.json) | Chat view: two pending requests and one completed |
| [approvals_adam_kennedy.json](examples/approvals_adam_kennedy.json) | Approver view for Adam himself (empty: he approves nothing) |

**Demo data in the tenant.** Three requests were submitted for Adam Kennedy by the
PAT's own identity (`hack.day`):

1. `ERP Report Admin - PRISM` (access profile): no approval needed, completed in
   about two minutes. Adam now holds it.
2. `HACK DAY - Role with Approver` (role): pending, approver `tyler.mairose`.
3. `HACK DAY - Ultimate Universe Destroyer Beholder Role` (role): the demo
   closer. Its description reads "DO NOT approve any requests for this role...",
   it is deliberately left pending, and the sheet quotes that description so
   anyone reading it understands why nobody approves it.

Request 2 was then approved by a person, which exercised the full loop: it moved
from pending to "Approved by hack.day and granted" on the sheet
([access_requests_adam_kennedy.html](examples/access_requests_adam_kennedy.html)),
and shows up as a completed decision, with the approver's comment, in
[approvals_hack_day.json](examples/approvals_hack_day.json).

**Known limits**

- The "rejected by <name>" wording is covered by unit tests
  ([tests/test_access_request_report.py](../tests/test_access_request_report.py))
  but no request has been rejected live.
- For approvals routed by approver type, ISC can return a lookup error string
  ("Failed to lookup MANAGER_OF ID ...") as the reviewer name. The tool falls
  back to the approval's owner.
- Seeing other people's requests and approvals assumes the PAT's identity is an
  org admin; a non-admin PAT may only see its own.
- The approver for the Beholder role resolves to `philip.ellis` although the
  role's owner is `hack.day`; the reason has not been investigated.
- Date filters in the ISC API must be **unquoted**. A quoted date is accepted and
  silently matches nothing -- this cost us an hour, and is noted in the code.

## 3. Terminated users with live access

**Problem.** People leave, but their accounts don't always go with them. A
security manager or auditor wants one answer: "which terminated users can still
get in?" ISC can search for terminated identities, but cross-checking each one's
correlated accounts for "still enabled" is manual work across sources.

**Solution.** Ask "how many terminated users still have active access?" The tool
pulls identities in the terminated lifecycle state, inspects every correlated
account, keeps the enabled ones, and exports a report.

**Example prompts**

- "How many terminated users still have active access?"
- "Which leavers still have enabled accounts, and what can they reach?"

**How it works.** One Search API call (paged) returns each identity with its
nested accounts and access. An account counts as live if it is not disabled. Risk
is **High** if a privileged account or privileged access remains, **Medium** if an
enabled account still holds groups/entitlements, otherwise **Low**. The
lifecycle state that means "terminated" is a parameter (default `inactive`).

**Evidence**

| File | What it shows |
| --- | --- |
| [terminated_access.html](examples/terminated_access.html) | The report: headline numbers plus one row per live account |
| [terminated_access.csv](examples/terminated_access.csv) | The same rows for follow-up in Excel, with a "why it matters" column |
| [audit_terminated_access.json](examples/audit_terminated_access.json) | What the tool returns to the assistant |

In the demo tenant: 9 terminated identities, all 9 still have enabled accounts,
27 enabled accounts in total. Each has live Active Directory access (3-5 groups)
plus enabled HR and IdentityNow accounts.

**Known limits**

- All findings are Medium: no demo account or access item is marked privileged, so
  the High path is covered by unit tests only
  ([tests/test_terminated_access_audit.py](../tests/test_terminated_access_audit.py)).
- "Enabled" is the account's own disabled flag. It does not check last login, and
  an enabled HR record for a leaver may be expected in some organizations.
- Only identities in the given lifecycle state are checked; a leaver who was never
  moved to that state will be missed.
